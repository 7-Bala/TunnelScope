# EXP-04 reconfirmation on strongSwan 6.1.0 (T-021)

**Date:** 2026-09-12 · **Trigger:** T-021 — upgrading the PQ lab image from 6.0.2 to 6.1.0 to fix
CVE-2026-78133 (IKEv2 rekey-collision use-after-free, potential RCE, affects 6.0.0+).

**Question:** do EXP-04's four PQ-observability signals survive the version upgrade, or were they
an artifact of the specific 6.0.2 build?

**Method:** rebuilt `testbed-alice-pq`/`testbed-bob-pq` on strongSwan 6.1.0 (one-line tag change,
no other Dockerfile or config edits), reran the `classical-baseline` and `pq-mlkem768` arms, and
compared the same four signals from `experiments/exp04-pq-length-asymmetry/analyze.py` directly via
tshark on the new captures.

## Result: all four signals reproduced, byte-for-byte identical

| Signal | 6.0.2 (original) | 6.1.0 (this run) |
|---|---|---|
| 1 — `INTERMEDIATE_EXCHANGE_SUPPORTED` (16438) in `IKE_SA_INIT` | classical: absent · PQ: present | **identical** |
| 2 — `IKE_SA_INIT` size delta | classical 492/500 → PQ 508/516 (+16 both directions) | **identical**: 492/500 → 508/516 |
| 3 — `IKE_INTERMEDIATE` message count | classical: 0 · PQ: 3 | **identical**: 0 vs 3 |
| 4 — fragmentation | PQ initiator fragmented (2 pieces), responder not | **identical**: initiator 1268+132 bytes, responder 1200 bytes |

No new plugin-loading issues: none of 6.1.0's removed plugins (`af-alg`, `android-dns`, `blowfish`,
`charon-xpc`, `duplicheck`, `gcrypt`, `keychain`, `led`, `libfast`, `manager`, `medsrv`/`medcli`,
`padlock`, `smp`, `soup`, `tnc-ifmap`, `tnccs-11`, `tnccs-dynamic`) were in our explicit `charon.load`
list (we use `openssl`, not `gcrypt`).

## Conclusion

EXP-04's findings were not a 6.0.2 build artifact. `DEC-013`/`DEC-017` and the EXP-04 result in
`experiments/RESULTS.md` stand unchanged. The lab's known-RCE exposure (CVE-2026-78133) is closed.

Raw captures: `testbed/captures/classical-baseline-6.1.0.pcap`,
`testbed/captures/pq-mlkem768-6.1.0.pcap` (+ `.groundtruth.json` for each, T2 evidence from
`swanctl --list-sas`).
