# EXP-50 — Per-vendor fix templates: Libreswan and MikroTik RouterOS (T-123) — PRE-REGISTRATION (2026-10-05, before any template, test or lab run)

## Why
`tunnelscope/remediate/plan.py` has 17 hand-written plans, all in strongSwan `swanctl.conf` terms, and the only automated application path (dry run, snapshot, watchdog, rollback) is for the strongSwan lab. T-123 asks for per-vendor fix steps for the vendors T-120/T-118 cover, "one tested template per rule per vendor", with the strongSwan pipeline unchanged. Owner's batch order fixed the vendors: strongSwan (exists), Libreswan, MikroTik. Owner, 2026-10-05: "do whatever you want".
The point of a template is that the *same finding needs a different fix on a different device*. The first example is already in the vendor documentation (read, not recalled; see Sources): the strongSwan fix for V-207223 ("integrity SHA-384 or SHA-512") has no SHA-384 on RouterOS, whose `hash-algorithm` accepts `md5 | sha1 | sha256 | sha512` only, and RouterOS documents no post-quantum key exchange at all. So a copied command would be wrong or impossible there.

## What is built (fixed here)
- `tunnelscope/remediate/vendors.py`: a table of templates `VENDOR_FIXES[vendor][rule_id]` for `libreswan` and `mikrotik`, and `plan_for(..., vendor=None)`. `vendor=None` or `strongswan` returns exactly what it returns today. For the other vendors a plan carries: `vendor`, `change`, `commands` (lines to type, in the vendor's own syntax), `config_diff` (an illustration, flagged as an example as today), `verify` (the vendor command that shows the change took effect), `source` (the documentation page and section the keywords come from), `verification` (`"lab"`: applied to a running device by the harness and the tunnel re-checked; `"docs-only"`: keywords checked against the vendor's documentation, not run on a device) and `automated_fix_available: false` always (the safe-apply pipeline stays strongSwan-lab-only; DEC-033/DEC-034 are not extended).
- A rule with no honest template for a vendor returns `template: null` and a `reason` (for example "RouterOS documents no SHA-384 hash-algorithm"), never an invented command.
- Rules in scope (config-class, the 12 whose strongSwan plan is a config change): V-207205, V-207193, V-207223, RFC8247-DH-MUST, RFC8247-DH-OFFER, RFC8247-ENCR, DST-PQ-KE, DST-PQ-DOWNGRADE, RFC4301-CONFIDENTIALITY, RFC8221-AH-INTEG, RFC8221-AH-LEGACY, RFC8221-ESP-3DES. The five patch/investigation rules (the three CVE-WATCH, CVE-2026-78135, RFC4303-SEQ) get `template: null` with the reason "software patch or investigation, not a configuration change; see the vendor's own advisories", since no fixed-version claim is made here (CVE verification is T-161).
- The API (`POST` remediation plan) takes an optional `vendor`; an unknown vendor is an error, never silently strongSwan.

## Tests and bars
- **H1 (every keyword is documented):** a test parses every command of every template and requires each setting name and each value to be in the fixture's table for that vendor. One undocumented token fails H1.
- **H2 (Libreswan, lab-verified):** the existing Libreswan lab (two containers and the keyless router, as EXP-07). For each in-scope rule that has a Libreswan template: a pair is configured so that TunnelScope reports FAIL for that rule on the captured handshake; the template's lines are applied as written to both ends; the tunnel is re-established (ping passes) and captured again; TunnelScope then reports that rule PASS, and no rule that was PASS before is FAIL after. A rule whose weak state Libreswan 5.4 cannot be configured into is listed as "not reproducible" and its template is labelled `docs-only`. Reproducing arms are `verification: "lab"` only if they passed.
- **H3 (RouterOS):** every template is `docs-only` unless the RouterOS CHR lab (two CHR VMs, as EXP-26) is brought up and the same closed loop as H2 is run; any template that passes it is `lab`, any that fails is corrected or removed and the failure reported. If the CHR lab is not brought up, all RouterOS templates stay `docs-only`, and the product says so in the plan (`verification`).
- **H4 (strongSwan untouched):** for all 17 rules, `plan_for(rule, ..., detailed=True, include_exec=True)` with `vendor=None` and with `vendor="strongswan"` is byte-identical (JSON, sorted keys) to the same call on `origin/batch/m`; the existing remediation tests pass without edits.
- **H5 (nothing invented):** every non-null template has a `source` and a `verification`; every `template: null` has a `reason`; a test fails on an empty one.
- **H6 (API):** an unknown vendor is a 4xx with a message naming the supported vendors; no vendor gives the old answer.
- Tests are mutation-checked (a mutant that adds an undocumented token, drops `verification`, or changes the default output must fail a test).

## ADDENDUM A (2026-10-05, after an exploratory lab probe, before the scored lab run)
A first run of all 24 Libreswan arms (not scored; its output was deleted) found, and this addendum fixes, the following. None changes a bar's threshold.
1. **Harness fault:** the per-arm alias addresses were added after pluto had scanned the interfaces, so every arm failed ("neither left nor right match an interface"). The harness now adds every alias first and runs `ipsec whack --listen` once (as EXP-07's does). The first run is discarded.
2. **Second harness fault:** one capture (V-207205 after) was empty although the tunnel was up (a tcpdump start race). The harness now starts tcpdump with `-U`, waits for it, and redoes an arm (up to 3 times) whose capture has no packets while the tunnel came up; the attempt count is recorded.
3. **Regression means PASS to FAIL.** The scorer's first draft counted a rule that disappears (the AH rules do not apply after AH is replaced by ESP) as a regression; the PREREG says "PASS before is FAIL after", which is what is scored.
4. **Rules the wire cannot decide.** RFC8221-AH-INTEG (HMAC-MD5-96 and HMAC-SHA1-96 have the same 12-byte ICV on the wire) and RFC8221-ESP-3DES came out UNKNOWN before the fix (TunnelScope does not claim what the wire does not show); that is correct behaviour, not a template fault. For these two, the template's lines are still applied as written on the running pair and the check is Libreswan's **own** algorithm report (`ipsec up` / `ipsec status`): the weak state must show `HMAC_MD5_96` (respectively `3DES_CBC`) and the fixed state `HMAC_SHA2_256_128` (respectively `AES_GCM_16_256`) with the tunnel up and pings through. A template that passes this is labelled `lab-device-state` (not `lab`): the device accepted it and negotiated the new algorithm, TunnelScope could not see the weak state on the wire either way.
5. **Libreswan 5.4 facts found in the lab and the manual, used in the templates:** `ipsec auto` is deprecated (a warning is printed); the reload line is `ipsec replace <conn>`, which the harness now also runs on every established arm (rc recorded). `keyexchange=ikev1|ikev2` is accepted (the manual says it replaces `ikev2=`). IKEv1 is dropped by default (`ikev1-policy=drop`), so V-207205 only appears when an operator turned IKEv1 on; the template says so.

## ADDENDUM B (2026-10-05, after the Libreswan scored run, before any RouterOS device run): H3 is run as a one-device check, and a documentation claim is tested
Fixed now, before the RouterOS run:
1. **Why not the two-router closed loop of H3.** One RouterOS CHR VM is enough to answer what the templates claim (the device accepts the command and the setting changes); negotiating a tunnel between two emulated routers adds nothing to that and takes much longer. So H3 is run as: one CHR VM (RouterOS 7.24.4 stable, the arm64 image whose zip hashes to `6ba35e64bbfc31283c5b3fc2d4e42500df851362fb8934941436286f8b79ce12`, the same value EXP-26 recorded, QEMU 11.1.2, emulated Cortex-A72 as in EXP-26), with a weak configuration created through the REST API for each rule; the template's **command text, unchanged**, is run on the device through `/rest/execute`; the setting is read back through the REST API and must equal the template's value (and differ from the weak value); the template's `verify` command is run and must print the new value. A template that passes is labelled `lab-device-state` (no tunnel was negotiated); one that fails is corrected or removed and the failure reported. Nothing is claimed about negotiation on RouterOS.
2. **A claim the documentation makes is tested, not trusted.** The RouterOS page lists `hash-algorithm` as `md5 | sha1 | sha256 | sha512`, with no SHA-384; the `V-207223` template and the test `test_routeros_has_no_sha384...` were written from it. EXP-26's M5 arm configured `hash-algorithm=sha384` on RouterOS 7.24.4 and negotiated HMAC-SHA2-384-192 / PRF-HMAC-SHA2-384, so the page is out of date for this version. The device check therefore also tries `hash-algorithm=sha384` and records the answer; whichever way it goes, the template text and the test are corrected to what the device did, and the page's omission is reported as a documentation gap, not hidden.
3. **Negative check for the "no post-quantum" reason:** the device is asked to accept a few ML-KEM names for `dh-group` and `pfs-group` (`mlkem768`, `ml-kem-768`, `kyber768`); a refusal for all of them is recorded as evidence for the `template: null` reason on this version only.

## ADDENDUM C (2026-10-05, after a first RouterOS run that failed because of the harness, before the scored RouterOS run)
The first run of `chr_check.py` passed 0 of 10: 6 settings had changed as expected but the check read them back wrongly, and the 3 proposal rules and the policy rule looked unchanged. Two harness faults, found by running the same commands by hand on the device: (1) `/rest/execute` without `as-string` starts a background job and returns its id, so the read-back raced the job; with `as-string` it runs synchronously, returns the device's error text (an empty string for a successful `set`) and the printed output; (2) the policy lookup took the first policy, which is RouterOS's default template, not the lab's. The harness now runs every command with `as-string`, treats any non-empty reply to a `set` as an error, finds the lab's policy by its peer, and checks the `verify` command's output (the command as written, `print detail`) for the new value. The first run's output was overwritten and is not in the history. One more note for RESULT: `/rest/execute` accepts a `find` that matches nothing without an error, so the pass condition is the read-back of the setting, never the absence of an error.

## ADDENDUM D (2026-10-05, after the first scored RouterOS run, before its re-run)
The first scored run (kept as `results/summary-mikrotik-first-run.json`) passed **8 of 10** templates. The two that failed were template faults, which is what the check is for, and are corrected here before the re-run:
1. **RFC8221-ESP-3DES:** `enc-algorithms=aes-256-gcm` alone was refused by the device ("failure: AEAD already provides authentication"): RouterOS will not take GCM next to an `auth-algorithms` value other than `null`. The template now also sets `auth-algorithms=null`; the check now reads back every setting of the command.
2. **RFC4301-CONFIDENTIALITY:** the change worked (`ipsec-protocols` went from `ah` to `esp`) but the template's `verify` command still searched for the old value (`where ipsec-protocols=ah`), so it printed nothing. The verify command now looks for the new value.
Also found, by the SHA-384 probe of addendum B: **RouterOS 7.24.4 accepted `hash-algorithm=sha384`** (REST and CLI), which the documentation page does not list. The V-207223 template keeps the documented `sha512` as its primary advice and says in `why` that sha384 also worked on the device; the committed fixture records `hash-algorithm: sha384` as a device-verified extra. All six ML-KEM name probes (`mlkem768`, `ml-kem-768`, `kyber768` for `dh-group` and `pfs-group`) were refused with "invalid value", which supports the no-post-quantum `template: null` reason for this version only.
